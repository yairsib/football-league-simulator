# Football League Simulator

A full-stack **football league simulation and betting platform**: 14 real Israeli Premier League
teams play a complete double round-robin season whose results are generated by a skill-based,
probabilistic match engine, while registered users bet on the outcomes before each round.

- **Backend:** Java 17, Spring Boot 3.2, Spring Security (JWT + BCrypt), Spring Data JPA, H2 in-memory database
- **Frontend:** React 18 + TypeScript, Vite, React Router, Axios
- **Tests:** 212 backend unit tests (JUnit 5 + Mockito), 48 end-to-end browser tests (Playwright)

## Main features

- User registration and login (JWT-secured, email + password — password must be at least 8 characters with an uppercase letter, a lowercase letter, and a digit, e.g. `Secret123`)
- Role-based access: regular `USER` accounts vs a single configured `ADMIN` account (see `app.admin.email` in `application.properties`); only admins can access `/api/admin/**` and the Admin page
- Profile editing (update username/email; balance and password cannot be changed here)
- Starting balance of 1000 per user
- View all teams with skill attributes
- View team squads, lineups (starters/substitutes), and unavailable (injured/suspended) players
- View match schedule with pre-match odds and visible weather conditions, plus per-match lineups
- View finished matches' goalscorers (with assists), red cards, and **substitutions** in a chronological timeline; per-player career stats (goals/assists/red cards/suspensions)
- **Match substitutions** — each simulated match generates 2-5 substitutions per team at minutes 46-85; substitutions appear in the match details timeline (`63' Substitution — Maccabi Tel Aviv: Dor Peretz out, Ido Shahar in`); GK-for-GK / field-for-field rules enforced; emergency field-player-as-GK exception when no bench GK is available; goal/assist eligibility is minute-based (a player subbed off at minute 60 cannot score at minute 70; a player coming on at minute 60 can score from minute 60 onward; same for red cards)
- **Dashboard** — personal betting summary (balance, bet counts, profit/loss, potential winnings), season status panel, quick links, and league highlights (top scorer, leader team); next-action banner guides users toward the relevant page
- **Admin overview panel** — at-a-glance system state (data imported, schedule generated, round state, betting state) with a recommended-actions list so admins know the correct next step
- **Admin season reset** — ADMIN-only `POST /api/admin/season/reset` wipes match events, bets, and all season stats, refunds OPEN bet stakes, restores every team's skill/morale to its persisted season baseline (aborting atomically if any baseline is missing), then either regenerates a fresh schedule or resets existing fixtures in-place; optionally resets all user balances to 1000; never modifies user accounts, roles, passwords, or OTP sessions
- Place bets before a match starts (enforced server-side): single match-result (1X2) bets,
  combo (accumulator) bets, correct-score bets, handicap bets, and season-long champion/top-scorer bets
- Automatic bet settlement when a match completes
- Real-time balance updates
- Bet history per user
- Live league table (sorted by points, goal difference, goals for, name)
- Admin: seed teams, generate schedule, open betting for a round, simulate individual matches or full rounds
- Round order is enforced: a round cannot be opened for betting or simulated (and its matches cannot be simulated) until all previous rounds are FINISHED

## Match Simulation Algorithm

This section explains, in execution order, how the backend generates a match result. Everything below describes the current code in `SimulationService` (result generation, events, injuries, form) and the shared probability model in `OddsService`. The simulation is **probabilistic**: a stronger team is more likely to win, but never guaranteed to, and two simulations of the same fixture can produce different outcomes.

```
Available squad (FIT, not injured, not suspended)
        ↓
Team power  =  skill + morale + home advantage − missing-player penalty + lineup rating ± weather
        ↓
Win / Draw / Loss probabilities  (draw model + logistic home share + weather jitter + caps)
        ↓
Red card roll (8% per team)  →  probability adjustment if triggered
        ↓
One random draw picks the outcome  →  bounded random scoreline consistent with it
        ↓
Standings, points, and team form (skill / morale ±1)
        ↓
Injury & suspension progression, new-injury roll (10% per team)
        ↓
Event timeline: red card, 2–5 substitutions, goal + assist per goal (minute-based eligibility)
        ↓
Bet settlement (match bets, then season bets)
```

### 1. Base team strength

Each team's `skillLevel` (40–100) is the dominant input. The league data file gives each team a realistic reference skill; when the league is seeded/imported the **actual starting skill is randomised** as `reference + offset`, offset uniform in **−3..+3**, clamped to 40–100 (so top clubs stay top clubs but every fresh league differs slightly). That starting value is persisted as the team's `baselineSkillLevel` for the season. For every match a **team power** score is computed for each side:

```
teamPower = skillLevel
          + morale × 1.5
          + 4                        (home team only)
          − unavailablePenalty       (missing starters / substitutes, capped)
          + lineupStrengthAdjustment (available starters' average rating, capped ±3)
          + weatherImpact            (added to both teams — see §4)
          (floor: 1.0)
```

The home side is the only asymmetry: a flat **+4** power points. Nothing else differs between home and away. The power difference `diff = homePower − awayPower` drives everything that follows.

### 2. Morale

`morale` (0–10) enters only through the team-power formula, weighted **1.5 per point**. A full morale swing (0 → 10) is therefore worth 15 power points, versus up to 60 points of skill range, so skill remains dominant. Morale has no other effect inside a match; it changes *between* matches as described in §9.

### 3. Player availability

- A player is **unavailable** when they are suspended (red card) or injured with matches remaining. Both are simulation-generated only — no real-world injury data is ever imported.
- **Strength effect.** Each unavailable **starter** costs the team 2.0 power points and each unavailable **substitute** 0.8, capped at 8.0 in total. Teams with no squad data fall back to their `injuries` counter (1.2 per injury, cap 6.0).
- **Lineup rating effect.** The average rating of the available starters is compared to a typical value of 70; each rating point above or below adds or subtracts 0.2 power, capped at ±3.
- **Who is on the pitch.** The simulation builds its own list of available players (status `FIT`, zero injury and suspension matches remaining). Players flagged as starters in the league data who are available start the match; every other available player (original substitutes and the rest of the squad) forms the bench.
- **One source of truth for the matchday lineup.** The simulation and the Lineups page call the *same* `LineupService.generateEffectiveLineup` on the same squad query. Unavailable starters are replaced by the best-fit available player (same position first, then compatible positions, goalkeeper only by goalkeeper), so whenever enough eligible players exist each team kicks off with exactly the 11 shown on the Lineups page; the effective substitutes list is the bench the simulation substitutes from. An injured or suspended player therefore never appears in any event, and the replacement shown to the user is the one who can actually score, assist, or be substituted.

### 4. Weather

Every fixture is assigned one of six conditions when the schedule is generated — `CLEAR`, `RAIN`, `WIND`, `HOT`, `COLD`, `STORM` — chosen uniformly at random, together with a small stored `weatherImpact` value (`CLEAR` 0; `RAIN` −1/−2; `WIND` −1..+1; `HOT` −1; `COLD` −1..+1; `STORM` −2/−3). The Matches page shows the condition as an icon and label; the numeric value is not displayed.

What weather actually changes in the current implementation:

| Condition | Effect on win/draw/loss probabilities |
|---|---|
| `RAIN`, `STORM` | Draw probability **+0.02** (before clamping) |
| `WIND` | Random shift of up to **±0.06** moved between the home-win and away-win probabilities |
| `STORM` | Random shift of up to **±0.05** (in addition to the draw bonus) |
| `COLD` | Random shift of up to **±0.02** |
| `CLEAR`, `HOT` | No probability effect |

Two accuracy notes for the reader:

- The stored `weatherImpact` number is added to **both** teams' power, so it cancels out in the difference and has no practical effect on the probabilities or the score. Weather's real influence is the draw bonus and the random jitter above.
- Weather does **not** change how many goals are scored. The score generator (§7) never reads the weather. Earlier descriptions such as "rain means fewer goals" described intent, not behaviour, and have been removed from this README.

### 5. Win / draw / loss probabilities

The simulation and the 1X2 betting market use the **same** probability function (`OddsService.computeProbabilities`):

```
diff       = homePower − awayPower
drawProb   = clamp(0.28 − |diff| × 0.002, 0.16, 0.30)      (+0.02 in RAIN / STORM)
homeShare  = 1 / (1 + e^(−diff / 16))                        (logistic)
homeWin    = (1 − drawProb) × homeShare
awayWin    = (1 − drawProb) × (1 − homeShare)
→ weather jitter (§4)
→ favourite capped at 0.76, underdog floored at 0.04, draw re-clamped, then normalised to sum 1
```

Interpretation: an evenly matched fixture sits near 36 / 28 / 36. A 16-point power gap gives the favourite about 73 % of the non-draw mass; a 32-point gap about 88 %, before the 0.76 cap. The caps guarantee that even the weakest team always keeps roughly a 4 % chance.

**Important:** the probabilities used to decide the result are recomputed at kick-off, not read from the stored odds. Because the weather jitter is re-rolled and player availability may have changed since betting opened, the kick-off probabilities can differ slightly from the implied probabilities of the displayed odds. Odds are frozen at the moment betting opens and are never recalculated for existing bets.

### 6. Red cards

Each team **independently** has an **8 %** chance of receiving one red card in the simulated match. When triggered, the player is drawn from the effective starting XI (someone actually on the pitch) and the minute (1–90) is chosen at that point. A team can never receive more than one red card per match. **Timeline consistency is guaranteed:** the sent-off player is never selected for a substitution (so they cannot be substituted off before, or after, the card), stays active until the card minute, is removed from the active set from that minute on (no goals, assists, or substitutions afterwards), and no replacement substitution is synthesised for them — the team plays on with ten.

Before the result is drawn, a red card reduces the carded team's win probability by a random **15–25 %** of its current value. 70 % of the removed mass goes to the opponent's win probability and 30 % to the draw, after which the three values are renormalised. The card therefore makes the sanction meaningful without deciding the match on its own.

After the match the player receives a **one-match suspension** (status `SUSPENDED`, `redCards + 1`) and a `RED_CARD` event is recorded at the chosen minute. Because suspensions are decremented *before* new cards are applied, a fresh suspension is always served in the team's next match.

### 7. Randomness and score generation

1. One uniform random number in `[0, 1)` is compared against the cumulative probabilities `[homeWin, homeWin + draw, 1]` to select **home win, draw, or away win**.
2. A scoreline consistent with that outcome is then drawn uniformly:

| Outcome | Winner's goals | Other side's goals |
|---|---|---|
| Home win | 1–4 | 0 to (home goals − 1) |
| Draw | 0–3 each (same value) | — |
| Away win | 1–4 | 0 to (away goals − 1) |

That is the entire result generator. It is intentionally simple and bounded (no side scores more than 4). It is **not** a Poisson or expected-goals model; those exist only for pricing the correct-score and handicap betting markets (see *Relationship to betting markets* below).

Two draws of randomness happen here (outcome, then scoreline); further randomness enters via weather jitter, the red-card roll, injuries, substitution timing, and event minutes. No part of the pipeline is deterministic.

### 8. Substitutions and the event timeline

Once the score is known, the simulation builds a minute-by-minute event timeline per team:

- **Substitutions.** 2–5 per team (never more than the bench or the on-pitch count allows), at random minutes **46–85**, processed in minute order. The outgoing player is picked at random from those still on the pitch who have not already been replaced; the incoming player from the unused bench. A goalkeeper is replaced by a goalkeeper and an outfield player by an outfield player; if no bench goalkeeper exists, any bench player may come on as an emergency exception. A sent-off player is removed from the on-pitch list once their minute is reached and cannot be substituted afterwards.
- **Goals and assists.** For each goal in the score a minute **1–90** is drawn. The set of players *active at that minute* is computed from the starting XI plus substitutes already on, minus players already off and minus the red-carded player if their minute has passed (at the same minute, red card and substitutions are applied before the goal). The scorer is chosen by weighted random pick from the active set; with **75 %** probability a different active player is credited with the assist. Player `goals` / `assists` statistics and a `GOAL` event are recorded.
- **Weights.** Scorer weight = position base × (rating / 70) × 1.5 if a starter; assist weight = position base × (rating / 70).

| Position | Scorer base | Assist base |
|---|---|---|
| ST | 10 | 3 |
| LW / RW | 8 | 7 |
| AM | 6 | 8 |
| CM | 4 | 6 |
| DM | 2.5 | 3 |
| RB / LB | 1.5 | 6 |
| CB | 1.5 | 1.5 |
| GK | 0.1 | 0.1 |

A team with no squad data still gets a score and standings, but no player events are generated for it.

### 9. Post-match changes

- **Standings.** Played, wins/draws/losses, goals for/against, and points (3 / 1 / 0) are updated for both teams.
- **Form.** The winner gains `skillLevel + 1` and `morale + 1`; the loser gets `− 1` on both. Draws change nothing. Values are always clamped to **skill 40–100** and **morale 0–10**. Over a season this produces genuine momentum: form feeds back into the next match's team power.
- **Injuries.** After each match a team plays, its existing injuries and suspensions are decremented by one match (a player with both keeps `SUSPENDED` until the suspension clears, then `INJURED` until the injury clears, then `FIT`). Then, with **10 %** probability, one currently fit starter or substitute (any fit player as fallback) picks up a new injury lasting **1–5 matches** with a random description. The team's `injuries` counter is refreshed to the number of currently injured players.
- **Settlement.** All open bets on the match are settled at the odds saved when each bet was placed, and season markets (champion / top scorer) are checked. Simulating a whole round also marks the round `FINISHED`.
- **Season reset.** Because skill and morale drift during a season, **Admin Reset Season** restores every team's `skillLevel` and `morale` to the **persisted season baseline** — the randomised starting skill fixed at import (see §1), not the raw league-data number, and never a fresh random roll. The reset refuses to run if any team lacks a persisted baseline, so the league always returns to exactly the state it started the season in (see *Admin Season Reset* below).

### Relationship to betting markets

The betting engine is a separate consumer of the same team-power model, and it is important not to conflate the three layers:

**A. Match simulation** — the pipeline above. Result = one random draw against the win/draw/loss probabilities, then a bounded random scoreline.

**B. 1X2 betting odds (home / draw / away)** — computed by `OddsService.computeOdds` from the same probability function as the simulation, then converted to prices:

```
odds = 1 / (probability × 1.07)      // 1.07 = bookmaker margin (~7 % overround)
rounded to 2 decimals, bounded to [1.20, 15.00]
```

Odds are calculated when the admin opens betting for a round (or, if a match somehow has none, once at simulation time) and are saved on each bet at placement time; they are never recalculated retroactively. The simulation recomputes probabilities at kick-off (with fresh weather jitter and current availability) and then applies any red-card adjustment, so simulation probabilities and displayed odds are closely related but not identical.

**Frozen markets.** When betting opens, the 1X2 odds *and* the three European Handicap −1 prices are derived from **one** probability vector and stored on the match. `GET /api/matches/{id}/handicap-odds` serves those stored prices (identical on every call) and a handicap bet is booked at exactly the displayed price. Because both markets come from the same vector, `Home −1` is always longer than `Home Win` on the stored prices. Season reset clears all six frozen prices.

**C. Correct Score and Handicap markets — Poisson pricing model only.** These markets need a probability for every scoreline, so they use an expected-goals (Poisson) model driven by the same power difference:

```
expectedGoals[home] = clamp(1.35 × e^( diff / 28), 0.45, 3.2)
expectedGoals[away] = clamp(1.35 × e^(−diff / 28), 0.45, 3.2)
prob(h, a)          = poisson(h, expectedGoals[home]) × poisson(a, expectedGoals[away])
correct-score odds  = 1 / (prob × 1.15), bounded to [4.00, 80.00]
```

The handicap market anchors itself to the same 1X2 probability vector that priced the match when betting opened and uses this Poisson grid only to split home wins into "by exactly one" versus "by two or more" (see *Handicap Bets*). **None of this Poisson model is used to generate the actual match score** — the real scoreline comes from the bounded generator in §7. An instructor comparing the two should expect the correct-score market to price 0–6 goals per side while simulated results never exceed 4.

**D. Season markets (champion, top scorer)** use their own season-level strength formulas over all teams / players and are settled when the final round finishes; they do not feed into match simulation.

### How this satisfies the project requirement

The project brief asks for a match result generator whose parameters and additional factors are documented. The implementation maps to that requirement as follows:

- **Team skill influences probabilities.** `skillLevel` is the largest term in team power, and the power difference sets the home/away share of the non-draw probability through a logistic curve (§1, §5).
- **Morale influences team power.** Each morale point adds 1.5 power, a deliberately smaller weight than skill (§2).
- **Unavailable, injured, and suspended players affect strength and availability.** They reduce team power through capped penalties, are excluded from the starting XI and from scoring/assisting until they return, and suspensions arise from simulated red cards (§3, §6).
- **Weather introduces dynamic and random effects.** Rain and storms raise the draw probability; wind, storms, and cold add bounded random noise to the home/away balance (§4).
- **Randomness prevents deterministic outcomes.** The result, scoreline, red cards, injuries, substitution timing, and event minutes are all random draws constrained by the probabilities above, so the stronger side wins more often but not always (§6, §7, §8).
- **Skill and morale evolve after results.** Winners gain and losers lose one point of each, within fixed bounds, so team ability responds to performance across the season (§9).
- **Initial skill is random within a realistic band.** Each fresh league import draws every team's starting skill from its league-data reference ±3 and persists it as the season baseline (§1).
- **Season Reset restores baseline values.** The admin reset returns every team to the persisted starting skill and morale of that season — never a new random roll — so a season can be replayed from identical starting conditions (§9).

Together these produce different but realistic outcomes between simulations of the same fixture, while keeping every input traceable to a documented parameter.

## Squads & Lineups

- Each team has a squad of `Player`s with a position (`GK`, `CB`, `LB`, `RB`, `DM`, `CM`, `AM`,
  `LW`, `RW`, `ST`), rating, and status (`FIT`, `INJURED`, `SUSPENDED`), plus lineup placement
  (`starter` / `substitute` / `lineupOrder`) and a team `defaultFormation` (e.g. `"4-3-3"`).
- A player is never both a starter and a substitute. A player who is `SUSPENDED`, or `INJURED`
  with `injuryMatchesRemaining > 0`, never appears as a starter or substitute — they're listed
  separately as **unavailable players** (with `fullName`, `position`, `status`,
  `injuryDescription`, `injuryMatchesRemaining`, `injuryMatchesTotal`,
  `suspensionMatchesRemaining`).
- View a team's squad and lineup from `GET /api/teams/{teamId}/squad` /
  `GET /api/teams/{teamId}/lineup`, or both teams' lineups for a fixture plus its weather from
  `GET /api/matches/{matchId}/lineups` — surfaced in the **Matches** page's **View Lineups** modal,
  which shows e.g. "Dor Peretz — CM — Injured, 3 matches remaining" and "No unavailable players"
  when the list is empty.
- Squads/lineups render empty until real squad data is added to the real-data file and imported
  — see "Real League Data" below for how to fill them in.

### Effective lineups are generated dynamically (auto substitutions)

- The original imported squad roles (`starter` / `substitute` / `lineupOrder`) are the **baseline**
  and are never rewritten in the database — they stay exactly as imported.
- Every time a lineup is requested, `LineupService.generateEffectiveLineup` builds the **effective**
  lineup on the fly: unavailable starters (injured with matches remaining, or suspended) are
  removed and replaced by the best-fitting **available** player, and unavailable substitutes are
  simply dropped from the bench (the bench is then refilled from remaining available squad players).
- **Replacement selection** (`findBestReplacement`) scores candidates by: same position (highest),
  then a documented compatible-position fallback chain (e.g. a missing `CB` prefers another `CB`,
  then `RB`/`LB`, then `DM`; a missing `ST` prefers another `ST`, then `LW`/`RW`, then `AM`), then
  higher rating, with original substitutes preferred over additional non-lineup squad players, and
  no player ever selected twice. A goalkeeper slot is only ever filled by a goalkeeper.
- The effective lineup keeps **11 starters** whenever the team has at least 11 available players,
  and refills the bench toward **7 substitutes**; if a team genuinely can't field 11 (e.g. many
  simultaneous injuries), it returns as many as possible and adds a `lineupWarnings` entry.
- `TeamLineupResponse` gains three optional fields beyond the original shape: `effectiveLineupGenerated`
  (true when at least one starter had to be replaced), `lineupWarnings` (e.g. "Only 9 available
  players — team cannot field a full 11-player lineup."), and `replacedPlayers` — a list of
  `{ originalPlayerName, replacementPlayerName, reason, position }` describing each swap (reason
  is `"Injured"`, `"Suspended"`, or `"Injured + Suspended"`). The **Lineups** modal renders these
  as a small "Lineup adjustments" section, e.g. *"Omer Nir'on unavailable (Injured); replaced by
  Tomer Tzarfati"*, only when present — existing tests/clients that ignore the new fields are
  unaffected.
- A new red card or injury only ever changes **future** effective lineups — it never rewrites the
  `MatchEvent` history of matches that already finished.

### Injuries are simulation-generated only

- **Injuries are never imported from real-world sources.** All real players from
  `ligat-haal-2025-2026.json` are loaded with `status = FIT` regardless of what the source data
  says about their real-life fitness — `LeagueDataImportService` ignores any injury fields in the
  seed file. 365Scores/Transfermarkt/club-site injury status is not "actual" injury status here.
- Injuries are generated **only** by the backend match simulation (`SimulationService`): after
  each simulated match, each team has a small (10%) chance of one new injury among its currently
  FIT players (preferring starters/substitutes), with a random description (`Muscle injury`,
  `Ankle injury`, `Knee injury`, `Hamstring injury`, `Knock`) and a random duration of 1–5 matches
  (`injuryMatchesRemaining` / `injuryMatchesTotal`).
- Existing injuries count down by one match each time that player's team finishes a match. A
  freshly-generated injury is not decremented in the same match it occurred. When the countdown
  reaches zero, the player becomes `FIT` again (description cleared) and is available for future
  lineups. `Team.injuries` is kept in sync with the number of currently-injured players (those
  with `status = INJURED` and `injuryMatchesRemaining > 0`).
- Injury duration is always shown as **matches remaining**, e.g. "Injured — out for 3 matches" /
  "Injured — 3 matches remaining", never as a real-world recovery date.

## Match Events & Player Stats (Goals, Assists, Red Cards)

- Every `Player` carries simulation-generated `goals`, `assists`, `redCards`, and
  `suspensionMatchesRemaining` counters — like injuries, **always imported as zero** regardless
  of the player's real-world record; they only ever change as a result of simulated matches.
- While simulating a match, `SimulationService`:
  - Rolls an **8% chance per team** (max one per team) of a **red card**, decided *before* the
    score is generated so it can reduce that team's win/draw chances by **15–25%** for this
    match (mostly transferred to the opponent) — the carded player is immediately suspended
    (`status = SUSPENDED`, `suspensionMatchesRemaining = 1`) and excluded from goal/assist
    selection for the rest of the match.
  - Picks a **goalscorer** for each goal in the generated score via weighted random selection
    that favors attacking positions, higher ratings, and starters (falling back to substitutes,
    or skipping the event entirely if a team has no eligible players — e.g. an empty squad).
  - Attributes an **assist** ~75% of the time to a different team-mate via the same
    weighted-selection mechanism with assist-favoring weights.
  - Saves a `MatchEvent` (`GOAL` or `RED_CARD`) for each, with a minute (1–90) and description
    such as *"Dor Peretz scored, assisted by Kervin Andrade"* or *"Tyrese Asante received a red
    card"* — viewable via `GET /api/matches/{matchId}/events`.
- **Suspensions count down like injuries**, but starting from the player's team's *next* match —
  a freshly-issued red card is never lifted in the same match it happened. A suspended player is
  excluded from lineups (`unavailablePlayers`) the same way an injured one is, shown as
  "Suspended — N matches remaining".
- The **Matches** page shows a goals/red-cards summary under each finished match card
  (e.g. `12' Dor Peretz (assist: Kervin Andrade)`, `53' Tyrese Asante`), and the **Lineups**
  modal shows each player's goals/assists/red cards alongside their availability status.
- Individual stats are also available via `GET /api/players/{playerId}` and
  `GET /api/teams/{teamId}/players/stats`.

### Match details modal

- Every match card on the **Matches** page now also has a **View Details** button that opens
  a `MatchDetailsModal` showing, in one place: the match title, score/status badge, weather
  (condition + impact), odds (when available), a chronological **events timeline**
  (`12' GOAL — Dor Peretz, assist: Kervin Andrade`, `53' RED CARD — Tyrese Asante`, sorted by
  minute), and a short **unavailable players summary** per side (e.g. "Hapoel Beer Sheva
  unavailable: 2"). A "View Lineups" button inside the modal opens the existing `LineupsModal`.
- Empty states: the timeline shows **"No events yet"** for matches that haven't been simulated,
  and **"No recorded events"** for finished matches with no events (e.g. a 0-0 draw, or a match
  between squads with no imported players).
- This is purely a thin presentation layer over the **existing** read-only endpoints —
  `GET /api/matches/{matchId}/events` (already sorted by minute) and
  `GET /api/matches/{matchId}/lineups` (already includes `unavailablePlayers` per side); no new
  backend endpoint or DTO was needed (`MatchResponse` already carries score/status/odds/weather).
  Final visual design for the whole app remains a separate later phase.

### Stats pages

- A new **Stats** nav link / `/stats` page shows three tabs — **Top Scorers**, **Top Assists**,
  **Red Cards** — each a simple table (Rank, Player, Team, Position, stat value, Rating)
  backed by `GET /api/players/leaders?stat={goals|assists|redCards}&limit=20`
  (returns `PlayerStatsResponse[]`, sorted goals/assists desc → the other stat desc → rating
  desc → name asc, or red cards desc → name asc; an invalid `stat` returns `400`).
- The **Teams** page gained a **View Squad** button per team, opening a `TeamSquadModal`
  that lists every player on the team (starters, substitutes, *and* additional squad players —
  the full squad, not just the effective lineup shown in **View Lineups**) with role, rating,
  goals/assists/red cards, and current status — backed by the existing
  `GET /api/teams/{teamId}/players/stats`.
- Clicking any player row (in the leader tables or the squad modal) opens a small
  `PlayerDetailsModal` with the player's team, position, jersey number, rating,
  goals/assists/red cards, and status/availability.

## Combo Bets, Bet Slip & Edit/Cancel

Extends the single-bet flow to support combo (accumulator) tickets and lets users manage
their own OPEN bets.

- **Combo bets**: on the **Matches** page, each open-for-betting match card now also offers
  "Add to Bet Slip" buttons (Home / Draw / Away) alongside the existing **Place Bet** button —
  so a user can either place a single bet as before, or build a multi-match ticket. A new
  **Bet Slip** panel (bottom of the page) lists the selections, lets the user remove any of
  them, enter one stake amount for the whole ticket, and shows the live **total odds**
  (product of each selection's odds) and **possible win** (`amount × totalOdds`). Placing the
  combo requires **at least 2 selections** — the button stays disabled until then.
- **Backend**: `POST /api/bets/combo` validates 2+ selections, rejects duplicate matches in the
  same combo, snapshots each selection's odds at placement time (never recalculated
  retroactively, exactly like single bets), computes `totalOdds`/`possibleWin`, and deducts the
  single stake from the balance once. A combo is stored as one `Bet` (`betType = COMBO`) with
  its match predictions in a new `bet_selections` table (`BetSelection` entity, one row per
  selection with its own odds snapshot) — see `docs/database-plan.md`.
- **Settlement**: `settleBetsForMatch` now also re-evaluates every OPEN combo touching the
  finished match — if *any* finished selection lost, the combo is `LOST` immediately (even with
  other selections still pending); if *every* selection has finished and won, the combo is `WON`
  and the user is credited `possibleWin`; otherwise it stays `OPEN`. Settlement only ever acts on
  bets still `OPEN`, so re-running it never double-pays or double-refunds (idempotent).
- **Edit OPEN bets**: the **My Bets** page now shows **Edit** / **Cancel** buttons on every OPEN
  bet (single or combo) — never on settled/cancelled ones. Editing opens a modal:
  - *Single*: change the **amount** and/or **prediction**. Changing the amount deducts/refunds
    the difference from the balance (rejecting increases the balance can't cover); changing the
    prediction re-snapshots the odds at the match's *current* price and recalculates
    `possibleWin`.
  - *Combo*: change the **stake amount** (deduct/refund the difference, same as single). The
    backend (`PUT /api/bets/{betId}/combo`) also supports replacing the full selections list —
    re-validating and re-snapshotting odds exactly like placement — but the frontend keeps this
    minimal and only exposes the amount field for combos, per the prompt's "amount edit is
    enough for now" guidance.
  - Editing is rejected (`409`) the moment any involved match is no longer `BETTING_OPEN`, or
    the bet itself is no longer `OPEN`.
- **Cancel OPEN bets**: clicking **Cancel** asks for confirmation, then calls
  `POST /api/bets/{betId}/cancel`, which sets the bet to `CANCELLED`, refunds the **full stake**
  to the balance, stamps `settledAt` as the cancellation time, and permanently excludes the bet
  from settlement — a cancelled bet can never be edited, cancelled again, or settled. Cancelling
  is rejected (`409`) once any involved match is no longer open for betting. The frontend
  refreshes the user's balance and bet list immediately after a successful cancel/edit.
- **Compatibility**: `POST /api/bets` (single bets) and the existing `GET /api/bets/my(/open|/history)`
  endpoints are unchanged in behavior; `BetResponse` simply gained optional combo fields
  (`betType`, `totalOdds`, `selections[]`) — for SINGLE bets, `selections` mirrors the existing
  match/prediction/odds fields as a single-entry list, so the **My Bets** table can render single
  and combo rows with one shared "Type / Match / Prediction / Odds" layout. See
  `docs/api-plan.md` for full request/response shapes.

## Handicap Bets

Adds a third betting **market** — `HANDICAP` — alongside the existing `MATCH_RESULT` (1X2) and `CORRECT_SCORE` markets, for single bets only. Combo bets remain `MATCH_RESULT`-only.

- **European Handicap -1 for the home team**: the home team concedes a 1-goal head-start. Three outcomes:
  - **Home -1** (`HOME_MINUS_ONE`): home team wins by 2+ goals — home wins on the handicap
  - **Handicap Draw** (`HANDICAP_DRAW`): home team wins by exactly 1 goal — results in a handicap draw
  - **Away +1** (`AWAY_PLUS_ONE`): match is a draw or the away team wins — away wins on the handicap
  - **No pushes**: every handicap bet settles either WON or LOST. There are no refunds or voids.
- **Handicap Odds formula**:
  ```
  // Anchored to the real 1X2 probabilities for this match — not an independent model:
  [pHomeWin, pDraw, pAwayWin] = probabilities(home, away, weather, impact)   // the SAME vector that priced the 1X2 market when betting opened

  // Poisson goal grid (same expectedGoals as correct-score) used ONLY to split pHomeWin
  // into "won by exactly 1" vs "won by 2+":
  frac1 = P(margin == 1) / P(margin >= 1)   // from the Poisson grid, h,a in 0..6

  P(HOME_MINUS_ONE) = pHomeWin * (1 - frac1)
  P(HANDICAP_DRAW)  = pHomeWin * frac1
  P(AWAY_PLUS_ONE)  = pDraw + pAwayWin

  odds = round(1 / (probability * 1.10), 2)   // 1.10 = ~10% bookmaker margin
  odds bounded to [1.20, 25.00]
  ```
  The margin (1.10, ~10%) sits between 1X2 (1.07) and correct-score (1.15), fitting a 3-way market.
- **Settlement**: `diff = homeGoals - 1 - awayGoals`; HOME_MINUS_ONE wins if `diff > 0`, HANDICAP_DRAW wins if `diff == 0`, AWAY_PLUS_ONE wins if `diff < 0`. Winners receive `amount × odds` (snapshotted odds).
- **Place a handicap bet**: on the **Matches** page, each open-for-betting match card has a **Handicap** button, opening a modal with the 3 handicap options and their odds. Selecting one shows a live possible-win calculation; placing the bet (`POST /api/bets/handicap`) deducts the stake immediately.
- **My Bets**: handicap bets show market **"Handicap"** and the predicted outcome ("Home -1" / "Handicap Draw" / "Away +1").
- **Edit/Cancel**: an OPEN handicap bet can have its amount and/or selection edited (`PUT /api/bets/{betId}/handicap`) while the match is still open — changing the selection re-snapshots odds at the new selection's current price. Cancelling (`POST /api/bets/{betId}/cancel`) refunds the full stake, same as any other bet.
- **Compatibility**: `BetResponse` gained additive `handicapSelection` and updated `displayLabel`; existing `MATCH_RESULT`/`CORRECT_SCORE` bets are unaffected. See `docs/api-plan.md` for full request/response shapes.

## Admin Season Reset

The admin can reset the entire season to a clean "before Round 1" state from the **Danger Zone** section at the bottom of the Admin page, or directly via the API:

**Endpoint:** `POST /api/admin/season/reset` (ADMIN only)

```json
{
  "confirm": true,
  "regenerateSchedule": true,
  "resetUserBalances": false
}
```

`confirm: true` is required — the backend rejects the request with `400 Bad Request` without it.

**What the reset does (always):**
- Deletes all match events (goals, red cards) and all bets (single, combo, correct-score, handicap, champion, top-scorer)
- Refunds OPEN bet stakes to each user's balance before deletion — no money is lost unfairly
- Zeroes all team season statistics: played/won/drawn/lost/goals for & against/points/injuries
- Clears all simulation-generated player stats (goals/assists/red cards) and simulation-generated injuries/suspensions — every player returns to `FIT`
- Restores every team's `skillLevel` and `morale` to its **persisted season baseline** (`Team.baselineSkillLevel` / `baselineMorale`, fixed when the league was imported — the randomised starting skill of this season) — the simulation nudges both by ±1 per win/loss, so without this a reset would keep end-of-season values. The reset never rerolls: two resets give identical values. See *Team baseline contract* below

**Schedule options (`regenerateSchedule`):**
- `true` (default) — deletes all rounds and matches, then generates a brand-new double round-robin schedule with freshly assigned weather conditions
- `false` — keeps the existing fixture list but sets every match back to `SCHEDULED` (clearing score, 1X2 odds, frozen handicap odds, and betting status) and every round back to `NOT_STARTED`

**Balance options (`resetUserBalances`):**
- `false` (default) — OPEN bet stakes are refunded; all other balances are preserved
- `true` — after cleanup, every user's balance is forcibly set to 1000 (the starting balance), overriding any refunds or accumulated winnings

**What the reset never touches:**
- User accounts, roles, passwords, and OTP sessions
- Team names, IDs, formations, `displayName`, and crests (skill/morale are *restored to baseline*, not preserved)
- Player identities, positions, ratings, jersey numbers, and baseline lineup roles (`starter`/`substitute`/`lineupOrder`)
- The imported real-league JSON data (`ligat-haal-2025-2026.json`) — squad data is not re-imported by a reset

**Team baseline contract:** every team's persisted baseline is verified *before* anything is deleted or modified. If any current team has no persisted baseline (it was never imported properly), the reset aborts with `409 Conflict` ("Season reset aborted … No season data was modified") and the transaction rolls back — it never reports success with partially restored data. The baseline is created only by a pre-season league import/seed; a reset restores it and never generates a new random value.

The response body includes counts of deleted events/bets, reset teams/players, `teamBaselinesRestored`, refunded open bets, and whether a fresh schedule was generated. After a reset with `regenerateSchedule: true`, season betting (champion/top-scorer bets) reopens automatically — Round 1 exists and is `NOT_STARTED`, which is the condition `isSeasonBettingOpen()` checks.

## Real League Data (Israeli Premier League 2025/2026)

The 2025/2026 season's teams (and eventually squads/lineups) are loaded from a structured
JSON file rather than hand-written code, so real data can be filled in incrementally from
verified sources without backend changes.

**Where it lives:** `backend/src/main/resources/data/`
- `ligat-haal-2025-2026.schema.md` — full documentation of the JSON format, validation rules,
  and the squad-completeness summary report
- `team-squad-entry-template.md` — an annotated, copy-paste-ready template showing exactly how
  to fill in **one team's** entry (team object, player object, rating/starter/substitute/status/
  `dataSource` rules, and a full worked example using placeholder names clearly marked
  `DO_NOT_IMPORT`)
- `ligat-haal-2025-2026.template.json` — structural example (its team/players are clearly
  marked `EXAMPLE_TEMPLATE` in `dataSource` and are never imported)
- `ligat-haal-2025-2026.json` — the real seed file: 14 real Ligat Ha'Al teams with name, reference
  skill level, morale, formation and full real squads.
  On import each team's starting skill is randomised around the reference (±3) and persisted as
  the season baseline; the file itself is never modified by the application.
- **Import is pre-season only.** `POST /api/admin/data/import` (and the Admin button) is rejected
  with `409 Conflict` as soon as any season activity exists — a round opened for betting, a
  finished match, match events, or any bet. Re-importing mid-season would reset skill/morale and
  player statistics while results and standings remained, so the backend refuses it; run
  **Reset Season** first. Validation (`/data/validate`) stays available at any time.

**Bulk squad insertion workflow — how to fill in remaining real squads:**
1. Collect verified data from reliable sources, team by team:
   - **Transfermarkt** — for the squad list, positions, jersey numbers, and market-value tier
     (a useful guide when picking an internal `rating`, alongside the team's `skillLevel`).
   - **365Scores lineups** — for the recommended starting lineup and substitutes, when
     available (use this to set `starter`/`substitute`/`lineupOrder`).
   - **Official club pages or the Israeli Football Association** — for cross-checking name
     spelling, squad numbers, and positions.
   Follow `team-squad-entry-template.md` for the exact object shapes and rules.
2. Add `Player` objects to a team's `players[]` array following the documented schema, setting
   `dataSource` to where each player's data came from (e.g. `"Transfermarkt"`, `"365Scores"`,
   `"official"`, `"manual"`, or a combination like `"Transfermarkt + 365Scores lineup reference"`).
3. **Never invent player names or ratings — and never pad a squad to make it look complete.**
   If you can only verify part of a squad, enter only what you can verify and leave the rest
   out; a `PARTIAL` report is expected and safe. Remember that `skillLevel`/`morale`/`rating`
   are **internal simulation ratings**, not official ratings, and that
   injuries/suspensions/goals/assists/red cards are **app-generated only** — never enter
   real-world injury/suspension status (see "Injuries are simulation-generated only" above);
   any `status`/`injuryDescription`/`injuredUntilRound`/`injuryMatches*` values in the source
   JSON are ignored on import and every imported player starts `FIT`.
4. As an ADMIN, click **Validate League Data** (or call `GET /api/admin/data/validate`) to check
   the file. It reports clear `errors` (block import — e.g. wrong team count, duplicate names,
   duplicate player names, out-of-range values, invalid enum values, starter/substitute
   conflicts) and `warnings` (non-blocking — e.g. "squad is missing", wrong starter/substitute
   counts, duplicate jersey numbers/lineup orders) without writing anything to the database. The
   response also includes a **squad-completeness summary** (`squadSummaries`) — one row per
   team showing `playersCount`/`startersCount`/`substitutesCount`/`unavailableCount`, the
   `hasExactly11Starters`/`hasExactlyOneStartingGoalkeeper`/`hasAtLeast7Substitutes` checks, any
   `duplicateJerseyNumbers`/`duplicateLineupOrders`, `missingPositions`, and an overall
   `status` of `COMPLETE` / `PARTIAL` / `MISSING` — so it's easy to see at a glance which teams
   still need real squad data. The Admin page renders this as a
   **Team | Players | Starters | Subs | Status | Warnings** table under the validation result.
5. Click **Import League Data** (or call `POST /api/admin/data/import`) to seed/update teams and
   players. The import is an **upsert** — teams matched by `name`, players by
   `(team, fullName)` — so it never deletes existing data and never invents players for teams
   whose squad is still empty; it returns a summary of `teamsProcessed`, `playersProcessed`,
   `warnings`, and `errors`.
6. `POST /api/admin/seed` also prefers this real-data import when the file is present and valid
   (falling back to the original random 8-team demo seed otherwise), so a fresh environment
   gets the real 2025/2026 teams by default.

## Security Design

### Authentication & Authorization

- All protected endpoints require a valid JWT (Bearer token in `Authorization` header). The token is issued on login/register and carries the user's email as its subject.
- Two roles: `USER` (all registered accounts) and `ADMIN` (the bootstrapped admin account — see Admin Bootstrap below). The role is set at account creation time and never changed by registration or login.
- `/api/admin/**` endpoints require `ROLE_ADMIN`; all other protected endpoints require any authenticated user. Unauthenticated requests return `401 Unauthorized`; authenticated non-admin requests to admin endpoints return `403 Forbidden` — both as structured JSON (no HTML error pages).
- Frontend: the Admin link in the navbar is only shown to users with `role === 'ADMIN'`. Navigating to `/admin` as a regular user shows an access-denied message (enforced by `AdminRoute`). A stale or expired JWT triggers an automatic redirect to `/login` via the Axios response interceptor.

### Public Registration

- Public registration (`POST /api/auth/register`) always creates a `USER` account. There is no path through public registration that grants `ADMIN` role.
- Registering with the configured admin email is blocked with a generic error message — the response does not reveal that the email is special or already exists. This prevents account enumeration and privilege escalation via registration.
- No public login flow can promote a user to `ADMIN`. The admin role is assigned exclusively by `AdminBootstrapService` at startup.

### Admin Bootstrap

- The initial `ADMIN` account is created by `AdminBootstrapService` (`ApplicationRunner`), which runs once at startup when `APP_ADMIN_BOOTSTRAP_ENABLED=true`.
- Required environment variables:
  - `APP_ADMIN_BOOTSTRAP_ENABLED=true`
  - `APP_ADMIN_EMAIL` — the admin account's email address
  - `APP_ADMIN_INITIAL_PASSWORD` — must satisfy the password policy (8+ chars, upper/lower/digit)
- Bootstrap is idempotent: if an `ADMIN` account already exists, it does nothing. If a `USER` account already exists with the target email, it does **not** promote it — a separate admin must be created with a different address.
- No production admin credentials exist in the code. The only committed credentials are the **TEST-ONLY** admin account in `application-test.properties` (used for local grading and the E2E suite — see *Admin access for the demo* above). Because the database is in-memory and recreated on every start, bootstrap must stay enabled for every run; it is idempotent and safe to leave on.

### Admin Login: Email OTP (Two-Factor)

- Admin login is a two-step flow:
  1. Submit email + password at `POST /api/auth/login`. If credentials are valid and the account is `ADMIN`, no JWT is returned — instead, the response contains `adminVerificationRequired: true` and an `adminVerificationToken`.
  2. An OTP code is sent to the admin's email address. Submit the code and the verification token to `POST /api/auth/verify-admin-code`. A JWT is returned only after the code is verified.
- OTP security properties: BCrypt-hashed (raw code never stored or logged), 5-minute expiry, 3 maximum attempts (session invalidated after), single-use (consumed on first successful verification).
- If email delivery fails, the OTP session is immediately invalidated and a safe error is returned — the admin must retry the full login flow.
- The frontend shows an `AdminOtpModal` after a successful password check and navigates to the dashboard after successful OTP verification.

### Forgot Password / Password Reset

- Regular users can reset their password via a two-step flow:
  1. Submit email to `POST /api/auth/forgot-password`. The response is always a generic success message — it does not reveal whether the email exists (anti-enumeration). If the account exists, a reset code is sent by email.
  2. Submit the reset token, the code from the email, a new password, and a confirmation to `POST /api/auth/reset-password`.
- Reset code security properties: BCrypt-hashed, 10-minute expiry, 5 maximum attempts, single-use.
- If email delivery fails, the reset session is invalidated and a fake UUID is returned — the response is identical to the non-existent-email case to prevent enumeration.
- New passwords must satisfy the password policy and are stored with BCrypt. The user must log in again after a successful password reset.

### Email Configuration

- Real email sending is controlled by the `APP_MAIL_ENABLED` environment variable:
  - `APP_MAIL_ENABLED=true` — activates `RealEmailService` (JavaMailSender). Required SMTP environment variables (Spring Boot relaxed binding: `SPRING_MAIL_HOST` maps to `spring.mail.host`, etc.):
    - `APP_MAIL_FROM` — the From address for OTP/reset emails
    - `SPRING_MAIL_HOST` — SMTP server hostname
    - `SPRING_MAIL_PORT` — SMTP server port (default 587)
    - `SPRING_MAIL_USERNAME` — SMTP auth username
    - `SPRING_MAIL_PASSWORD` — SMTP auth password
  - `APP_MAIL_ENABLED=false` (default) — activates `NoOpEmailService`, which throws a safe config exception for any delivery attempt without logging or returning any code. Admin OTP and password reset flows will error safely.
- No SMTP credentials are committed. OTP/reset codes are never logged or returned by any API response in normal runtime.

### Test-Only Mail Endpoint

- A test mail capture endpoint (`GET /api/test/mail`) exists **only** when **both** of the following are true:
  - `SPRING_PROFILES_ACTIVE=test` (Spring test profile active)
  - `app.otp.test-mode=true`
- Under these conditions, `FakeEmailService` (marked `@Primary`) captures all sent OTP/reset codes in memory, and `TestMailController` exposes them for retrieval.
- The main `SecurityConfig` never exposes `/api/test/**`. A separate `TestSecurityConfig` (`@Profile("test")`, `@Order(1)`) handles test routes with `securityMatcher("/api/test/**")` so they are completely isolated from the production security chain.
- This endpoint is used exclusively by the E2E test suite to retrieve codes without a real mail server.

### Ownership Checks

- `GET /api/bets/my`, `PUT /api/bets/{betId}`, `POST /api/bets/{betId}/cancel`, and all market-specific edit endpoints verify that the bet belongs to the authenticated user before acting. Requesting another user's bet returns `404 Not Found` (not `403`, to avoid disclosing existence).

### Password Policy

- Passwords must be at least 8 characters and contain at least one uppercase letter, one lowercase letter, and one digit (e.g. `Secret123`). This is enforced via `@Pattern` on `RegisterRequest` and validated on the server — the frontend shows the rule on the registration form but the backend is the authoritative check.
- Passwords are hashed with BCrypt before storage; the plaintext password is never persisted or logged.

### Rate Limiting (Login)

- Failed login attempts are tracked in memory per email address (case-insensitive). After 5 failed attempts within a 10-minute sliding window, further login attempts for that address return `429 Too Many Requests`. The counter resets on a successful login or after the window expires.
- This is an in-memory, single-instance implementation — it resets on application restart and does not coordinate across multiple instances. It is intended as a basic brute-force speed bump for local/demo use, not a production-grade defence.

### Error Handling

- The global exception handler (`GlobalExceptionHandler`) catches all unhandled exceptions and returns `"An unexpected error occurred"` — never a stack trace or internal message. Specific business errors (not found, conflict, validation, rate limit) return structured JSON with appropriate HTTP status codes.

### CORS

- The backend allows cross-origin requests only from `http://localhost:5173` (configurable via `app.frontend.origin` in `application.properties`). Methods `GET`, `POST`, `PUT`, `DELETE`, and `OPTIONS` are allowed; credentials are not sent.
- In the Vite dev server, the `/api` path is proxied to `localhost:8080`, so the browser never makes a direct cross-origin request during development. The CORS config applies to direct API access (e.g. curl, Postman, or a separately hosted frontend).

### Known Limitations (Local Dev / Demo Only)

- H2 in-memory database. The web console is **disabled by default** and `/h2-console/**` is not permitted through Spring Security; it is enabled only under the `dev` profile (`application-dev.properties` sets `spring.h2.console.enabled=true`, which also switches on the `/h2-console/**` permit rule and the frame-options relaxation). Never run the `dev` profile outside a local machine.
- JWT secret is a static string in `application.properties` — rotate it and store it as an environment variable before any non-local deployment.
- **All data is in-memory**: users, bets, teams, and results live in an H2 in-memory database that is recreated on every backend restart. Register/seed again after restarting.
- Rate limiting and OTP sessions are in-memory only (reset on restart, not shared across instances).
- Admin OTP login provides two-factor authentication for the admin account. Regular users do not have 2FA. No refresh tokens; no account lockout beyond the 10-minute rate-limit window.
